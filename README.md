# x-ui-inbounds-setup

Автоматическая настройка эталонных инбаундов **Trojan-gRPC** и **Hysteria2** для панели 3X-UI
и **перенос инбаундов между серверами** с полным сохранением клиентов.

Версия **2.0** — безопасная переработка по итогам аудита 24.09.2026 (все пять обязательных
правок реализованы; см. «Что изменилось в v2.0» ниже).

---

## 🚀 Возможности

| Режим | Команда | Назначение |
|---|---|---|
| Локальный | `bash setup-inbounds.sh` | создать/обновить эталонные Trojan-gRPC + Hysteria2 на этом сервере (клиенты сохраняются) |
| Экспорт | `bash setup-inbounds.sh export [FILE]` | консистентный вывоз локальных инбаундов и клиентов в JSON (на исходном сервере) |
| Импорт | `bash setup-inbounds.sh import FILE` | ввоз инбаундов из файла экспорта (на целевом сервере): сопоставление по `remark+protocol` — есть → обновить, нет → добавить |

Флаги: `--dry-run` (только план), `--yes` (без подтверждения), `--force-master`
(осознанный запуск на мастере с нодами — без него записывающие режимы на мастере блокируются).

## 🚀 Установка одной командой (с сервера)

```bash
wget --inet4-only --timeout=30 --tries=3 -qO /tmp/inb.tar.gz \
  https://codeload.github.com/Michael-K-cloud/x-ui-inbounds-setup/tar.gz/refs/heads/main \
  && tar -xzf /tmp/inb.tar.gz -C /tmp \
  && bash /tmp/x-ui-inbounds-setup-main/setup-inbounds.sh --dry-run
```

> ⚠️ Используйте именно архив `codeload.github.com` одним файлом и `--inet4-only`:
> пофайловое скачивание с `raw.githubusercontent.com` на некоторых серверах обрывается
> (один из IP Fastly может быть недоступен), а исходящий IPv6 может зависать.
> Старый вариант `bash <(wget -qO- .../raw/.../setup-inbounds.sh)` не рекомендуется.

## 🐛 Какие проблемы решает скрипт

- Ручное создание инбаундов: неправильные TLS/ALPN/fingerprint → протоколы не работают или легко блокируются.
- Баг панели с `localhost` в share-ссылках → скрипт фиксирует корректный `webDomain`.
- Забытые порты в UFW → открываются автоматически с комментариями, устаревшие правила подчищаются.
- Ручная настройка маскировки Trojan-gRPC через nginx (`grpcs://`) → добавляется автоматически с бэкапом, `nginx -t` и автооткатом.
- **Настройка нового сервера с нуля** → `export` на рабочем сервере + `import` на новом: инбаунды и клиенты переносятся 1-в-1, uuid/пароли/ключи НЕ перегенерируются — ссылки клиентов продолжают работать (при совпадении домена и свободных портах).

## 🛡️ Безопасность (v2.0)

1. **Консистентный бэкап до любых изменений**: `sqlite3 .backup` (Online Backup API) +
   `PRAGMA integrity_check` + счётчики. Без годной точки отката скрипт не пишет.
   Бэкап: `/root/backups/inbounds-setup/<дата_время>/x-ui.db`.
2. **Все записи — при остановленной панели, в одной транзакции** (`BEGIN IMMEDIATE … COMMIT`);
   при любой ошибке — `ROLLBACK`, панель запускается обратно, БД остаётся нетронутой.
   `integrity_check` и счётчики сверяются до и после.
3. **Схема БД читается через `PRAGMA table_info`** — никакой хардкод-колонки
   (`client_stats` и др.); несовместимая схема → понятный ABORT до записи.
4. **Только локальные инбаунды (`node_id=0`)**: инбаунды нод на мастере не удаляются и не
   меняются. Запуск на мастере без `--force-master` заблокирован.
5. **Зависимости чистятся до удаления**: `client_inbounds`, `client_traffics`,
   `inbound_fallbacks` — без сирот.
6. **Существующий инбаунд обновляется НА МЕСТЕ** (id, порт, serviceName, tag сохраняются) —
   ссылки клиентов и nginx-локации не ломаются. Удаление — только для дубликатов.
7. **Учётки клиентов переносятся 1-в-1**: единый реестр полей (union по всем локальным
   инбаундам) — trojan-`password`, hysteria-`auth`, uuid сохраняются независимо от порядка
   строк. Генерация нового секрета — только если у клиента его никогда не было, с явным
   предупреждением в выводе.
8. Живая БД читается только `mode=ro&immutable=1` (правило проекта после инцидента 13.09).
9. nginx: бэкап с именем, зафиксированным один раз, `nginx -t`, reload только при успехе,
   иначе автооткат. UFW: правила с комментариями, защита от накопления мусора.
10. Файл экспорта содержит данные клиентов → создаётся с правами `600`, в репозитории и
    логах не публикуется, после переноса рекомендуется удалить.

## 📋 Пример: перенос инбаундов на новый сервер

```bash
# ── на ИСХОДНОМ сервере (панель НЕ останавливается) ──
bash setup-inbounds.sh export
# → /root/inbounds-export-<host>-<дата>.json  (права 600)

# скопируйте файл на целевой сервер, например:
scp /root/inbounds-export-*.json root@НОВЫЙ_СЕРВЕР:/root/

# ── на ЦЕЛЕВОМ сервере ──
bash setup-inbounds.sh import /root/inbounds-export-*.json --dry-run   # план
bash setup-inbounds.sh import /root/inbounds-export-*.json            # применение
```

Логика импорта:
- инбаунд с такими же `remark`+`protocol` уже есть → **UPDATE** (клиенты из источника;
  порт, stream_settings и tag целевые — работающие ссылки не ломаются);
- нет → **INSERT**: порт источника сохраняется, если свободен (прямые ссылки не меняются),
  иначе выбирается свободный с предупреждением; домен, пути сертификатов и порт в
  `externalProxy` переписываются под целевой сервер; `serviceName` сохраняется (nginx-location добавится);
- на панелях с нормализованными таблицами (`clients`/`client_inbounds`, форк x-ui-pro)
  скрипт синхронизирует их best-effort и честно сообщает о результатах.

## ⚙️ Требования

- **ОС:** Ubuntu 22.04 / 24.04, `root`, `python3`, `sqlite3` (CLI).
- **Панель:** установленная 3X-UI (в т.ч. форк `mozaroc/x-ui-pro`).
- **SSL:** валидный сертификат домена в `/root/cert/<домен>/` (Let's Encrypt через панель).
- Переопределяемые пути (редко нужны): `XUI_DB`, `XUI_CERT_DIR`, `XUI_NGINX_CONF`,
  `XUI_SERVICE`, `XUI_BACKUP_ROOT`, `XUI_CONFIG_JSON`.

## 🛠 Совместимость (честно)

Проверено автоматическими тестами (мок-БД обеих схем): логика БД совместима со схемами 3.3.1 и 3.8.5
(колонки берутся из `PRAGMA table_info`, неизвестная схема → ABORT до записи).

- ✅ Одиночный сервер без нод — основной сценарий.
- ⚠️ Мастер с нодами — только `--force-master`; инбаунды нод (`node_id != 0`) не трогаются.
- ⚠️ Форк x-ui-pro с таблицами `clients`/`client_inbounds`: синхронизация связей —
  best-effort (состав колонок форка может отличаться); после запуска проверьте клиентов в UI.
- ⚠️ Панели 3.7+ с **Managed Hosts** (таблица `hosts`): поле `externalProxy` может
  игнорироваться — скрипт предупредит; после запуска проверьте порт Trojan в подписке
  (ожидается прямой порт, а не `:443`).

**Обязательно**: первый запуск — на тестовом сервере. Порядок проверок:

```bash
bash setup-inbounds.sh --dry-run
bash setup-inbounds.sh
sqlite3 "file:/etc/x-ui/x-ui.db?mode=ro&immutable=1" "PRAGMA integrity_check;"
sqlite3 "file:/etc/x-ui/x-ui.db?mode=ro&immutable=1" \
  "SELECT id,remark,port,protocol,node_id FROM inbounds;"
```

## Что изменилось в v2.0 (кратко)

Старая версия (до 2.0) содержала критические дефекты: `cp -a` живой WAL-базы вместо
консистентного бэкапа; запись в БД при работающей панели; `DELETE FROM inbounds`
без фильтра `node_id` (на мастере удалялись инбаунды нод) и без чистки зависимостей;
хардкод-колонка `client_stats` (INSERT падал на схеме 3.3.1); перегенерация
trojan-паролей/hysteria-ключей у клиентов в зависимости от порядка строк; смена
`serviceName` у работающего Trojan (мертвые nginx-локации). Всё это исправлено;
добавлены режимы `export`/`import` для переноса между серверами.

Файл `_setup-inbounds_22092026.sh` — историческая копия владельца, не используется.
